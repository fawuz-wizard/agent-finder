## Problem Statement

Orange's head of sales keeps the agent network in a hand-made Excel file: aggregator, agent, location as text, region, status. He asked for "a map" of every agent in the country that he can zoom in and out of, with no further instruction. The shape of the thing is ours. A map that only shows pins would show one pin today and would not answer the question he actually asks his file: how many agents do we have, and how many are working, in each region and under each aggregator. The design gives the map that job and lets the pins fill in by themselves as aggregators confirm shops.

Numbers in this document come from the development database on 2026-10-11, where the Orange import has been applied: 95 agents, 4 aggregators, 24 distinct cleaned towns, 18 agents with no region, 1 agent located, 0 confirmed. The pilot database will show the same shape once the import is applied there (a precondition, see Dependencies).

## Demand Evidence

- The head of sales at Orange asked for it in person: "said they would like to have it, he will be the head" (the first user and the owner of the Orange side).
- He is the person who "instructed them to give us the data": the agent file the import pipeline was built on.
- Honest grading: this is a sponsor's wish ("if we could provide a map for him it will be nice, that's all"), not a job he already does with a tool. The count table is what turns the wish into a daily tool. Until he opens it on a normal Tuesday, demand is unproven.

## Status Quo

The Excel file of aggregators and agents kept by hand at Orange; the file we received is a copy of it. It answers counts and knows nothing of place, freshness or whether a shop exists. It is the competitor: the map must beat it on counts first, then add what a spreadsheet cannot (place, confirmation, photos, app activity).

## Target User and Narrowest Wedge

- **User:** the head of sales at Orange, judged on whether the network is growing and working where Orange needs it. Second user: each aggregator, who gets the same screen scoped to their own agents.
- **First question the screen must answer:** "How many agents do we have, and how many are active, in each region and under each aggregator?" (chosen over coverage gaps, verifying shops, and live presence, which become layers later).
- **Wedge:** the count table with drill-down national → region → aggregator → agent, drawn on the country, with two activity columns that match his own file on day one.

## Constraints

- Customers never see money; the national screen shows no balances or float figures in the first version either ("balances where authorised" from the Orange meeting is a later permission).
- The app never changes an agent's status by itself; the map reads, it never writes.
- Wrong role gets 404, not 403. Scope is derived from the signed-in account, never from the request: there is no parameter that asks for a wider scope.
- Demo (mock) mode equals live: the demo reimplements the aggregation in TypeScript over the seeded demo network, and a fixture test compares its output with the API's JSON for the same seed.
- No new technology: the Google Maps wrapper, loader and key already planned for the pilot; no second map library, no geocoding API, no styled Map ID.
- The Orange file's addresses are never altered; towns are geocoded once by hand into a checked-in table that becomes the single town → region source for the import as well.
- Not built now. Built after the aggregator screens move to the finder design, with the aggregator's scoped map designed here so both share one component.

## Definitions (stated once, used everywhere)

- **Registered:** every agent row in scope, whatever its status. Inactive-at-Orange agents are counted here, shown greyed on the map when confirmed, and never counted as transacting.
- **Transacting (Orange file, Apr 2026):** the agent is active at Orange and the transaction count imported from the file is above zero. An agent with no file figure (registered in the app, not in the file) shows "no file figure" and is left out of this column's denominator, never counted as zero. The file month is a constant kept beside the import and sent in the payload's definitions; when Orange's feed exists this column becomes live and the label changes.
- **Using the app (7 days):** at least one availability declaration (any presence) or one recorded transaction by the agent inside a rolling window of 7 × 24 hours ending at the time the summary is generated. A sign-in alone does not count. Computed from the two event tables with two grouped queries over the window, never per agent.
- **Located:** the agent has a point (own pin or aggregator placement). **Confirmed:** the aggregator confirmed the point; only confirmed shops get a pin on the map.
- **Unplaced:** no town on record, or a town not in the towns table. Shown as their own row (same five counts) with a reason, and as one hollow bubble anchored off the coast at 7.90, −13.60 labelled "no place on record". Never silently dropped.

## Premises (agreed, "we change in building")

1. The map belongs to the Orange side (the national view the meeting asked for), the head of sales its first user. Aggregators get the same map scoped to their own agents. One component, two scopes.
2. Its first job is counts: registered and activity, per region and per aggregator, with drill-down national → region → aggregator → agent. Pins and photos sit underneath, only for confirmed shops.
3. **Revised after the cold read.** No single word "active". Two labelled columns side by side, Transacting and Using the app, as defined above, with the definitions printed in the column headers.
4. Orange users are issued accounts like everyone else (one-time code, then their own PIN). No new role: a dealer-type account with no region, permissions `VIEW_AGENT` and `VIEW_NATIONAL` only, no manage or financial grants. It owns no agents, so the other console tabs are empty for it.
5. Built after the aggregator redesign; the aggregator's own map is designed now so the two share one piece. (The cold read argues the sponsor should get it first; the user's call is "don't build it now".)

## Approaches Considered

- **A: Counts first, no map tiles.** National count table with drill-down and a four-region outline. Smallest build, works with today's data. Not chosen: the sponsor asked for a map, and nothing improves as pins arrive. It survives as the first half of B.
- **B: Country map with counts, pins underneath.** Chosen.
- **C: B plus live customer-search heat.** Where customers look and find nobody, drawn over the agents. Not chosen now: empty until the finder has weeks of real traffic, and search points would need a new table and a privacy note. Listed as a later layer.

## Recommended Approach: B

**Screen** (route `/dealer/map`; its own full-width layout outside the 480 px console frame, the aggregator side's first desktop layout):

- Left: the count table. Rows: national → the four regions → aggregators (recursive through sub-aggregators) → agents. Columns at every level: Registered · Transacting · Using the app · Located · Confirmed. Definitions in the header. Clicking a row filters the table below it and moves the map: a region row fits the bounds of that region's towns; an aggregator row fits the bounds of its agents' towns, or the whole country when it has none; an agent row centres on its pin when confirmed, else its town.
- Right: the map (Google Maps, the existing wrapper extended only with `onReady`; bounds through `fitBounds`, markers from the marker library already loaded). Two layers by zoom: below zoom 12, one bubble per town with a count label (Registered / Transacting); at zoom 12 and above, confirmed pins only, each opening a sheet with the shop's name, aggregator, the five counts' row for that agent and the shop photo when there is one. No province polygons: the regions live in the table, which avoids sourcing and licensing a boundary dataset and the five-region question (the 2017 North West province is folded into North by the import's table today).
- A permanent line above the map with live numbers: "0 of 95 shops confirmed on the map". That number is the feature in the first weeks: it is what the head of sales pushes down to aggregators.
- Export: the existing report CSV, which gains the same filters (`region`, `aggregator`, `city`) and the national scope for the Orange account.
- Scope: the same screen inside the aggregator console shows only that aggregator's agents and their sub-aggregators', same columns, same map.

**API** (no migrations):

- `VIEW_NATIONAL` added to the permission set. A scope helper returns all agents for that permission, otherwise the aggregator's own agents collected through `parent_id` by iterating until no new ids appear, capped at five levels. Wrong role 404. Scope comes from the principal only.
- `app/domain/activity.py`: `transacting_orange(agent) -> bool | None` (None when there is no file figure) and `app_active(events, transactions, now, window: timedelta) -> bool`. Pure functions, pinned-clock tests. Never writes `agent.active`.
- `GET /api/v1/dealer/map/summary`: `{generated_at, definitions: {transacting, app, file_month}, totals: Counts, regions: [{region, ...Counts, aggregators: [{id, name, ...Counts}]}], towns: [{city, region, lat, lng, ...Counts}], unplaced: {...Counts, reasons: {no_town, town_not_on_record}}}` where `Counts = {registered, transacting, no_file_figure, app_active, located, confirmed}`. No money fields, by test.
- `GET /api/v1/dealer/map/agents?region=&aggregator=&city=`: rows from the existing report rows, lat/lng only when confirmed, photo URL only when on the map, greyed flag for inactive at Orange.
- `apps/api/data/towns.json`: every distinct cleaned town → lat/lng/region, hand-checked. The import script reads this table instead of its own town → region list, so there is one source of truth (a precondition task, done before the map).
- Demo: the web demo reimplements the aggregation in TypeScript; the demo seed gains agents in all four regions and one sub-aggregator so the national view has something to show; a fixture test compares demo output with the API JSON for the same seed.

**Why B:** he asked for a map; the counts give it a job he has today; the pins and photos arrive on their own as the agent app and the aggregator console do their work, so the map gets better every week without anyone editing a file.

## Later layers (not in the first version)

- Big-screen mode for a wall at HQ: hidden chrome, auto-refresh, idle cycling through regions, a view-only token with a short session. Unasked; it drags in a styled Map ID and session questions.
- Province shading (needs a boundary dataset and a decision on the fifth province).
- C: customer-search heat.
- Balances where authorised.

## Open Questions

- The 7-day window and whether a sign-in with no action should ever count. Decide with the head of sales once he has seen the two columns.
- Who geocodes and checks the towns table before the build.

## Success Criteria

- The head of sales opens the screen on a normal week without being asked, and stops asking an aggregator for the count of agents in a region.
- The Transacting column matches his file for every aggregator on day one.
- "Confirmed on the map" rises week on week after launch (the number he pushes down).
- Every aggregator sees only their own agents; a test proves aggregator A cannot read B's numbers, and the Orange account reads all.
- No money field appears in any map payload, by test; counts sum to totals at every level, by test; demo equals live on the seeded network, by test; the summary runs in a fixed number of queries whatever the agent count, by test.

## Dependencies

- The Orange import applied to the pilot database.
- The towns table, hand-geocoded and checked, and the import script switched to it.
- The aggregator screens moving to the finder design (the user's build order), including a full-width layout this route can use.
- The Google Maps key for the pilot, restricted by HTTP referrer to the console host and to the Maps JavaScript API.
- A way to create the Orange account with `VIEW_AGENT` + `VIEW_NATIONAL` (a permissions flag on the account scripts), then a one-time code through the flow shipped on 2026-10-11.

## The Assignment

Before anything is built, show the head of sales a one-page mock-up of the count table alone (regions × the five columns, with the two activity definitions in the header) and ask him to check the Transacting column against his file. If he corrects a number, we learn his definition of active. If he asks "where is the map?", we have the demand we wanted.
